# 正式文件交付与可用性检查

本参考是剪映任务的文件交付标准。素材库导入、时间线拖入以及旧版替换均由用户自己完成；AI 完成制作、同步和交付前检查，给出已检查的正式文件链接。检查责任覆盖素材、全片时间安排与合成关系、最终文件，不能把用户手动操作解释成由用户负责排错。用户已经明确：导入后不再自动检查剪映素材库或时间线；不代导入、不代拖入、不代替换，也不为可用性测试写入剪映。

## 三类交付前检查责任

- **素材内容。** 核对本次实际使用及复用的原片、截图、录屏、图片、字体、声音和派生层：内容/版本正确，路径及依赖可读，清晰度和真实字形够用，精确文案/数字/Logo 与来源相符。已核实且未变化的证据可复用，不重做无关检查。
- **全片时间安排与合成关系。** 核对最终主片到源片的入出点、剪切/速度映射，字幕和动作落点，全片覆盖与合法留白、首尾和衔接，层级/遮罩/全屏覆盖，原声仅一份及声音归属。对本次新增/改动的实际组合，必须按交付顺序将原片对应帧与所有正式层合看，相关声音同段合听；结果证据保留在 work/，不需要导入剪映或另导整片测试成片。只看孤立透明层、只听孤立音效，不能记为合成关系已通过。
- **最终正式文件。** 对真正交付的封装文件做下述技术与内容检查，确认新文件身份、完整性、格式与规格、真实透明、画面和声音，以及链接指向这份文件。用户只负责导入、拖入和替换，不承担字体、同步、图层、声音或编码修复。

三类检查复用当前 plan、build 与实际观察记录，最后在同一份交付记录列明素材检查、时间安排/合成检查、文件检查的状态及证据，并绑定当前文件的绝对路径与 SHA-256。有必需缺口即不能记为可用交付。这里的“时间安排检查”指交付文件内已经排好的全片时序，不表示已修改或验收用户之后手动放置的剪映时间线。

## 交付什么

开始实际制作前，依据当前请求和已有上下文，用一句话声明本次产物与范围并继续；普通口播沿用完整透明包装，不让用户每次重新选择工具或格式。只有缺失信息会实质改变产物且无法由现有要求确定时，才询问具体缺口。

| 实际产物 | 选择条件与可用范围 |
| --- | --- |
| `overlay` 全片透明包装（默认 4A） | 一条同画幅、帧率、00:00 起点和全片长度的主包装 MOV；声音能可靠嵌入则嵌入，必要才增加同基准人物层或独立音轨。指定全屏区间可不透明，其他叠加区间保持 Alpha；原口播保留在原工程，不重复混入。内部文字/关键帧是烘焙画面。 |
| `final_video` 完整成片 | 用户明确要求整条成片文件时，才合成原片、人声、包装和对应声音；说明它是已渲染视频，不称内部对象仍可原生编辑。不因此自动从剪映保存或导出工程。 |
| `audio` 仅声音文件 | 本次仅改声音或要求音频交付时，交付已对齐的正式音频；实际剪辑仍核对源时间与相关混音，不强制生成无关视频或空视觉层。 |
| `subtitle` 字幕文件 | 明确要求字幕交付时，保留实际支持的文字/时序；SRT 不承载任意艺术字位置、字形或关键帧。独立脚本对照纠错遵循 srt-script-corrector 自身结构/文字检查，不误套无视频的合成验收，也不声称已核听。 |
| `hybrid` 混合独立可编辑文件（4B） | 明确要求混合可编辑时，组合实际支持的字幕、独立音轨与必要烘焙层，逐项说明可编辑字段；不因该目标改为 AI 操作当前工程。 |
| `draft` 剪映可编辑草稿 | 仅明确要求草稿时生成，保留实际可编辑范围，结构/依赖与原生可打开证据分别核对；没有可打开依据就不能当可用工程交付。普通 JSON、源码和清单不是可以拖入素材库的视频。 |

明确要求混合可编辑时按 [4B 文件分工](../../package-talking-head-video/references/hybrid-editable.md) 选择真实可用产物，不进入当前剪映建轨/替换。独立短动画或素材按明确时长交付，不强制伪装为全片包装。SRT、JSON、源码、分镜或渲染日志不能代替本来应交付的媒体。

## 成片分辨率与画质

确认 SRT 后、制作前，用 FFprobe 读取用户提供的主视频原文件，记录视频流宽高及旋转方向，以实际显示方向锁定成片宽高。默认保持主视频实际分辨率、方向和比例。横屏 1920×1080 交付 1920×1080，竖屏 1080×1920 交付 1080×1920。横屏 1280×720 交付 1280×720，竖屏 720×1280 交付 720×1280。独立插入的录屏、图片、B-roll 或代理文件不决定全片尺寸。用户明确要求改分辨率或画幅时按本次要求执行。

内部预览可降分辨率。正式合成从主视频原文件取画面，按锁定的目标尺寸渲染，避免经过低分辨率中间片再放大。保留视频画面且支持复制视频流时直接复制，需要重编码时采用高质量设置，尽量一次最终编码，避免为缩小体积过度压缩。以典型改动区间的原尺寸画面核对细节、文字边缘和运动画面的压缩块。尺寸一致只是技术检查的一项。

交付前把从源片锁定的目标宽高传给现有技术检查器的 `--width` 和 `--height`，由它读取最终文件核对实测宽高。检查目标取自制作前记录的源片或本次明确要求。低清预览、尺寸不符或重编码后出现明显画质下降时，修正渲染或编码并重检后交付。

## 交付前必须通过

1. **正式文件完整。** 等待渲染、编码、音频封装全部成功结束；确认最终路径存在、可读、非空。检查最终封装文件，不用中间无声版或旧版结果替代。生成 SHA-256；检查后改了文件就重新检查。
2. **媒体技术正确。** 对每个正式媒体运行下面的检查脚本：解析真实流信息、从头到尾解码、核对解码帧数与目标帧数、尺寸、精确帧率、媒体流起点及视频/音频时长、音轨有无。这里的全文件解码是技术检查，不是逐帧审美验收，也不创建测试片或剪映测试工程。
3. **透明与可见内容真实存在。** 叠加素材检查 Alpha 像素格式，并在每个应透出原片的语义区间选代表帧核实实际透明像素；在各个有内容的场景选择可见帧，避免整层空白。全屏区间另看边缘覆盖与人物窗口，不把有 Alpha 通道等同于实际透明。精选字幕的合法留白及辅助层延迟出场继续有效。
4. **正式画面和声音已检查。** 风险分类与连续查看标准执行 [制作检查](production-checks.md)，稳定区间关键帧、高风险短动态连续查看；复用 [正式输出局部检查](../../package-talking-head-video/references/revision-workflow.md) 的提取物与观察，不重复做一套验收。首次制作检查每个新增场景的关键动作、落稳/阅读态、边界与首尾；返修看改动及依赖；重做按本次实际重做范围检查。结合实际叠加组合核对字形、截字、人物/字幕遮挡、证据可读性、转场及源时间映射。新增或改动声音须实际核听其区间，核对落点、尾音和口播遮蔽；无声任务记录 UISFX 留白及音轨决定。不能读取必需画面或声音时，状态为未完成检查，不能填通过。
5. **剪映兼容路径有依据。** 按 [制作检查中的兼容判断](production-checks.md) 将实际容器、视频编码/像素格式/Alpha、音频封装、色彩/HDR 及所用功能与已有实测范围逐项对应，记录沿用或需重核的理由。小补丁差异本身不一律重测；配置/功能变化或异常须重核相关路径。无适用依据或必要重核无法完成时不作为可用交付，不代导入测试，不把历史记录当本文件已原生验证；草稿另需可打开证据。
6. **整包同步无须用户补修。** 核对所有媒体从 00:00 起、同一工程帧基准与全片长度，人物与主片源映射一致；多层顺序和音频归属清楚。交付只需用户导入、按必要层级放到 00:00，不再找秒数、调速、补静音、抠绿幕、改字体或重编码。

技术脚本使用现有本地 FFmpeg/FFprobe，不下载依赖。示例参数必须替换成本次实际值；所有检查结果留在任务 `work/`：

```bash
python3 <video-editing-playbook>/scripts/verify_delivery.py \
  --file /task/outputs/全片包装_v1.mov --kind overlay \
  --width 1920 --height 1080 --fps 30000/1001 --frames 2100 \
  --audio present --alpha-frame 0 --alpha-frame 900 --visible-frame 30 \
  --ffmpeg /existing/ffmpeg --ffprobe /existing/ffprobe \
  --out /task/work/全片包装_v1.technical.json
```

`--alpha-frame` 和 `--visible-frame` 可重复，帧号从 0 开始；前者按设计覆盖应透明区间，后者覆盖有内容场景。有意全屏的不透明视频用 `--kind video`；全片独立音轨用 `--kind audio --audio present`，省略宽高及画面帧参数，仍给相同 `--fps` 与 `--frames`。`--audio absent` 用于不应有音轨的包装/人物层。单独无声动画与独立音轨各自检查；不强制给留白任务生成空音轨。已有 build 哈希时必须另传 `--expected-sha256`；返修或重做必须通过可重复的 `--previous-file /task/outputs/上一版.mov` 指明旧交付路径，检查器拒绝将同一路径当作新交付。该检查发生在文件生成后；制作前仍必须选定不存在的新输出路径并拒绝覆盖。

`verify_delivery.py` 成功只表示 `technical_pass`；它不替 agent 看图、听音或判断兼容，也不直接授权交付。每个正式媒体的技术报告与素材、时间/SRT、画面/声音及兼容观察，必须进入 [统一交付清单](handoff-manifest.md)。独立字幕纠错、独立素材等非剪辑任务按自身产物的适用检查，不硬套无关的全片/SRT 合成条件。

## 最终核对入口

实际剪辑的首次交付、返修和重做都执行：

```bash
python3 <video-editing-playbook>/scripts/finalize_delivery.py \
  --manifest /task/work/handoff-v2.json --out /task/work/handoff-v2-ready.json
```

清单字段、证据绑定和适用检查只在 [handoff-manifest.md](handoff-manifest.md) 维护；沿用现有 plan/build、技术报告和实际观察，不重建另一套制作计划。该入口绑定当前真实制作计划，复用现有 UISFX 检查器验证当前 SRT/计划的选声或留白绑定，再核对素材与正式文件哈希、当前版本、时间/SRT 锚点、风险区间观察、技术与兼容结果、全部旧/新交付身份，成功后生成 `delivery_ready=true` 及正式 Markdown 链接。未完成、错版、文件变化或缺必需证据时，结果不通过且没有可用交付链接；修正当前问题后核对新版，不以手填标志或旧版通过记录绕过。

最终回答直接使用核对结果返回的链接，不从目录按文件名另选一份。文件在核对后又被改动时重新检查。该入口只核对记录和文件一致性，不证明 agent 真的观察了内容，也不代表用户审美认可；实际观察责任继续按本文件与制作检查执行。

## 不通过与返修

明确问题按原范围最多自动返修两轮，修后检查新正式文件及受影响区间；整包最终媒体技术检查仍须通过。两轮后仍有问题、检查能力缺失或兼容性无法确认时停止循环，报告未完成项。不能为了到达轮数上限而放宽“可以用”的标准，不能把未通过文件链接成可用成品。允许分别交付已独立通过、不会使用户承担修复或逐场拼接的可用部分，但整体任务保持未完成；失败片、中间文件和仅供诊断文件留在 `work/`。

返修或者重做必须生成新的正式文件，使用未占用的新绝对路径/版本名，旧正式文件及原始素材保留。缓存和未受影响素材可以复用，但本轮重新交付的主包装必须是新文件；不能通过覆盖、移动/改名旧文件或继续发旧链接冒充新交付。完成本轮检查后给出新文件的可点击链接，由用户自己替换，本流程不进入原生替换/重新关联入口。

## 交付后结束

每次首次交付、返修或重做，都在 Codex 展示并给出可点击链接，链接使用最终核对入口本轮成功结果生成的正式链接，路径与哈希绑定同一份正式文件。多文件时用简短表格列出每个文件链接、用途、从下到上的层级、带声音与否、00:00 对齐、替换哪一版或本轮复用状态。明确“文件已制作并通过交付检查，尚未由 AI 导入或放入剪映”，给出必要层级和 00:00 对齐说明。展示工具不支持 Alpha MOV 时保留原文件链接及已查看的必要帧，说明展示限制；不改交黑底 MP4、不把预览限制当作文件损坏。交付后结束，不等待用户拖入，用户导入后不再自动检查剪映素材库或时间线，不追加整片播放听审，不主动保存、重开或导出用户剪映工程。
